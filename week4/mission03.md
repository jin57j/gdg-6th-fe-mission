1. 프로그래밍 및 프론트엔드에서의 상태(State)는 일반적인 프로그래밍에서의 상태란 시간이 지남에 따라 변할 수 있는 데이터이다 현실 세계에서 '뜨거운 커피'가 시간이 지나 '차가운 커피'로 변하는 것처럼, 프로그램 안에서도 변수나 객체의 값은 계속해서 변화한다.문자열, 불린값, 배열, 객체 등 다양한 데이터 타입이 모두 상태가 될 수 있다.

2. 상태를 관리해야 하는 이유는 전통적인 자바스크립트 방식에서는 상태가 바뀔 때마다 개발자가 직접 DOM을 조작하여 화면을 갱신해야 했기 때문이다. 관리가 안 되었을 때의 문제점 연쇄적 부작용이 생길 수 있다. 하나의 상태 변경이 수많은 UI 노드와 다른 상태들을 연쇄적으로 건드려 코드가 얽히고설키게 될 수 있다. 애플리케이션이 커질수록 어떤 데이터가 언제, 왜 바뀌어서 이 화면이 나왔는지 추적하기가 불가능해진다. 테스트 및 유지보수 악화 상태 로직과 UI 로직이 강하게 결합되어 독립적인 테스트가 어려워진다.

3. Context의 사용 createContext()를 통해 데이터 보관함을 만든다. Context 제공하기 (Provider): 상위 컴포넌트에서 형태로 하위 트리에 데이터를 주입한다. Context 사용하기 (Consumer): 데이터가 필요한 깊은 곳의 자식 컴포넌트에서 useContext() Hook을 호출해 값을 곧바로 꺼내 쓴다. Context는 전역적으로 유용하지만 남용하면 컴포넌트의 재사용성이 떨어진다는 단점이 있다.

4. Context API가 있는데도 외부 라이브러리를 쓰는 이유 Context API는 엄밀히 말하면 상태 관리 도구라기보다는 상태 전달 도구에 가깝다. 대규모 애플리케이션에서 Context만으로 상태를 관리하려고 하면 몇 가지 명확한 한계에 부딪칠 수 있다 . 불필요한 렌더링 Context는 단일 값을 전송하도록 설계되어 있다. 만약 하나의 Context 객체 안에 여러 상태가 들어있을 때 하나의 정보만 바뀌어도 참조하던 컴포넌트들까지 전부 리렌더링된다. Provider Context를 통해 상태를 공유하려면 JSX 트리 상단에 해당 <Context.Provider>를 감싸주어야 한다. 공유할 상태가 많아질수록 컴포넌트 최상단이 수많은 Provider로 뒤덮여 가독성이 떨어지고 유지보수가 힘들어진다. 복잡한 비동기 처리의 부재 현대 웹 앱은 API 요청(비동기 데이터)을 처리하는 로직이 핵심이다. Context API는 자체적으로 비동기 미들웨어나 상태 변화 시점을 제어하는 기능을 제공하지 않기 때문에, 비동기 처리가 복잡해지면 개발자가 직접 구현해야 하는 번거로움이 있다.

5. 라이브러리: Zustand 많은 라이브러리 중 최근 프론트엔드 생태계에서 가장 높은 성장세와 선호도를 보이는 Zustand는 Flux 구조로 애플리케이션의 상태를 하나의 커대한 단일 스토어(Store)에 담아두고 관리하는 방식이다. Zustand의 핵심 특징 단순하고 직관적인 보일러플레이트 과거 대세였던 Redux는 (Action),(Dispatch), (Reducer), (Type) 등 아주 작은 상태 하나를 바꾸기 위해 작성해야 하는 보일러플레이트가 너무 많았다. 반면 Zustand는 단 몇 줄만으로 스토어를 생성하고 사용할 수 있다. Provider가 필요 없는 코드 Zustand는 리액트 컴포넌트 트리 밖에 훅(Hook) 형태로 전역 상태를 생성한다. 따라서 최상단에 컴포넌트를 감싸는 <Provider>가 필요 없다. JSX 구조가 깔끔하게 유지된다.
